## 1. AI를 사용한 업무

### 업무 배경
- **업무**: OK Cashbag 서비스군(OCB) 31개 레포지토리 보안 정기진단
- **진단 항목**: SQL Injection, XSS, 파일처리 취약점, 데이터 보호(CORS/Secrets/JWT/암호화/PII), 오픈소스 CVE(SCA) — 총 5개 영역
- **기존 방식으로 31개 레포 전부 진단 시 예상 소요**: 수작업 기준 수개월

### AI 적용 핵심 영역 3가지

#### ① 취약점 자동 탐지 — LLM 교차검증 (LLM-Check)
- Python 정적 분석 스크립트(SAST)로 1차 후보 추출
- Claude가 소스코드를 직접 읽고 **실제 취약 여부를 재검증**
- FP(오탐) 필터링 + 증거 코드 스니펫 자동 추출

#### ② 보고서 자동 생성
- 진단 결과 JSON → Confluence 보고서 자동 변환
- 취약점별 코드 확인 결과·위험 시나리오·조치 권고 자동 작성
- 담당자는 최종 검토·판정만 수행

#### ③ 진단 기준 자기 갱신 (Audit 피드백 루프)
- 담당자 판정 중 발생한 기준 결정이 자동 기록
- 반복 패턴 → 진단 기준(Memory)으로 자동 축적
- 이후 동일 유형 발생 시 AI가 동일 기준을 자동 적용

## 2. 기존 처리 방식

### 수동 진단 프로세스
```
레포 clone
  → grep/IDE로 위험 패턴 탐색 (SQL 쿼리 직접 검색, XSS 패턴 수동 추적)
    → 코드 흐름 수동 추적 (Controller → Service → DAO → Query)
      → 취약 여부 판단
        → 보고서 Word/HWP 수기 작성
          → 검토 및 수정
            → 게시
```

### 수동 방식의 한계
| 한계 | 구체적 문제 |
|---|---|
| **속도** | 레포 1개당 평균 1~2일 소요. 31개 = 31~62일 이론값 |
| **일관성** | 담당자별 판단 기준 차이 발생 (동일 패턴인데 위험도 다름) |
| **누락** | 수동 grep으로는 코드 흐름 추적 한계 — 간접 주입 경로 미탐 |
| **보고서 품질** | 취약 코드 증거 스니펫 수동 복사·붙여넣기 오류 |
| **재사용성** | 진단 분야별 가이드라인 문서 + 개인 노하우로 기준은 있으나, 매번 사람이 직접 열어 대조해야 적용됨. 서비스 특성 변화·시간 경과에 따라 기준 자체도 주기적 갱신 필요 |

### 실제로 놓치기 쉬운 패턴 — 왜 grep만으로는 부족한가

실제 진단에서는 `keyword`처럼 특정 변수명이 아니라 **`$`** 로 grep해서 MyBatis Mapper XML의
`${}` 직접 삽입 패턴부터 찾는다 — SQL Injection 후보를 가장 빠르게 좁히는 방법이기 때문이다.

```
Mapper XML: LIKE '%' + ${keyword} + '%'   ← '$' 검색으로 바로 발견되는 지점
    ↑ query.getKeyword()
Service:    ItemQuery.builder().keyword(request.getKeyword()).build()
    ↑ request.getKeyword()
Controller: @RequestBody SearchRequest request
```

`$` 검색으로 Mapper의 위험 패턴 자체는 금방 찾아진다. 문제는 그 다음이다 — 이 `${keyword}`가
**실제로 외부 사용자 입력과 연결되는지는 Mapper에서 Service, Controller 방향으로 거꾸로
추적해야** 확인 가능하다. 이 역추적을 사람이 손으로 하면 파일을 오가며 시간이 오래 걸리고,
중간에 DTO/Map으로 한 번 감싸져 있으면 "내부 값이겠지"라고 넘겨 미탐(False Negative)으로
이어지기도 한다. 이 역추적을 AI가 대신하도록 표준화한 것이 뒤에서 소개할
**프롬프트 — 역추적형 교차검증**이다.

## 3. AI 사용 후 달라진 점

### Before / After 핵심 비교

| 항목 | 기존 (수동) | AI 적용 후 |
|---|---|---|
| 레포 1개 진단 | 1~2일 | **2~4시간** (LLM 교차검증 포함) |
| 31개 레포 전체 | 이론상 2~3개월 | **약 3주** (병렬 진행) |
| 보고서 초안 작성 | 담당자 직접 수기 2~3시간 | **자동 생성 5분** |
| 오탐 처리 | 발견 후 개별 확인 | LLM 1차 필터 후 담당자 최종 판정 |
| 판단 기준 축적 | 가이드라인 문서 + 개인 노하우로 존재, 매번 사람이 찾아 대조해야 적용 | Memory로 자동 축적, 다음 리뷰부터 자동 적용 |

### 실제 수치 (2026년 진단 결과)
- **진단 레포**: 31개 (OCB 서비스군 전체 중 일부)
- **총 스캔 후보**: 1,931건 (5개 영역 합산)
- **LLM 교차검증 후 최종 Finding**: 248건
- **오탐 필터링**: 68건 제거 (오탐률 27.4%)
- **보고서 발행**: 31개 레포 Confluence 페이지 자동 게시
- **위험도 자동 분류 후 담당자 조정**: 13건 (전체의 5.2%)

### 담당자 역할 변화
```
기존: 탐색(60%) + 분석(30%) + 보고서(10%)
현재: 탐색(0%) + 판정·검토(70%) + 기준 개선(30%)
```
> AI가 "찾는 일"을 하고, 담당자는 "판단하는 일"에 집중

**근거**: AI가 1,931건 후보를 스캔·분석하고, 담당자는 최종 248건 판정 + 위험도 조정 13건에만
직접 관여했다 — 전체 후보의 약 13.5%만 사람 손을 거쳤다.

## 4. 실제 산출물

### 산출물 1 — 자동 생성 보고서 (Confluence)

**구성 섹션:**
- 1.1 진단 개요 (서비스 특징, 기술스택, 진단 범위)
- 2.1 취약점 개요 (AI 자동 작성 — 개발자 대상 2~3문장)
- 2.2 취약점 요약표 (항목별 위험도·파일:라인)
- 3.x 취약점 상세 (코드 스니펫 + 공격 시나리오 + 조치 권고)
  - 각 항목마다 `:::expand "코드 직접 확인 결과"` 블록 포함

**예시 — AI 자동 작성된 취약점 개요:**
> "본 서비스에서 SQL Injection 및 민감정보 로그 노출 취약점이 확인되었습니다. 공격자가 파라미터를 조작하여 데이터베이스 내 회원정보를 탈취하거나, 운영 로그를 통해 인증 토큰을 수집할 수 있습니다. 해당 파라미터에 PreparedStatement 적용 및 민감정보 로그 출력 제거를 권고합니다."

### 산출물 3 — 자동 축적된 진단 기준 (Memory)

Audit 중 발생한 판정 기준이 자동으로 문서화된 예시:

```
feedback_log_dto_severity_standard.md
  → 운영 로그 PII 노출: 취약/High
  → 디버그 로그 PII 노출: 정보/Medium
  (2026-06-12 <your-repo> 리뷰에서 확정)

feedback_conservative_security_policy.md
  → SQL ${} 직접 삽입: 입력 경로 무관하게 취약/High
  → SpEL StandardEvaluationContext: 항상 취약/High
  (2026-06-23 <your-repo> 리뷰에서 확정)

feedback_hardcoded_credential_severity.md
  → dev/default 프로파일이 운영과 동일 자격증명 공유: 취약/High
  → dev/default 프로파일이 운영과 다른 자격증명 사용: 취약/Medium
  (2026-06-25 <your-repo> 리뷰에서 확정 — "dev 설정이니 Medium"으로 넘어갈 뻔한 항목을
   담당자가 운영 설정파일과 직접 대조해 자격증명이 동일함을 확인하고 상향)

feedback_sca_review_policy.md
  → LLM 교차검증이 완료된 오픈소스 CVE(SCA) findings는 건별 재판정 생략, 일괄 정탐 처리
  (반복 확인 단계를 줄이기 위해 확정된 처리 방침)
```

> 이 기준들은 한 번 확정되면 **이후 모든 레포 리뷰에 자동 적용**된다. 담당자가 같은 질문을
> 두 번 하지 않아도 되는 것이 핵심 — "기준을 만드는 일"에 쓴 시간이 다음 레포부터는 전부
> 절약되는 시간으로 돌아온다.

## 5. 다른 사람도 재사용 가능한 프롬프트나 절차

### 핵심 원칙: "AI에게 역할을 주고, 사람은 판단만"

---

> 아래 6개는 번호가 아니라 이름으로 구분하고, 목적에 따라 3개 그룹으로 묶었다
> (탐지 정확도 → 판정 근거 → 산출물 자동화 — 실제 진단 흐름과 동일한 순서).
> 각 항목은 **실제 사례 → 사용한 문구 → 결과** 3단 구성으로 동일하게 정리했다.
> "문구"는 실제 프롬프트에서 그대로 발췌한 핵심 문장이고, "결과"는 그 문구를
> 썼을 때 실제로 얻어낸 값(정탐/오탐 판정, 위험도, 소요시간 등)이다.

---

### 그룹 1 — 탐지 정확도를 높이는 프롬프트 (실제로 취약한가?)

#### ① 역추적형 교차검증 (Injection)

**실제 사례**: 스캐너가 keyword 파라미터를 SQL Injection 후보로 탐지했지만,
Mapper XML의 `${}` 삽입 패턴만으로는 실제로 외부 입력이 도달하는지 확신할 수
없었던 경우 (§4 "기존 방식의 한계"에서 다룬 사례와 동일)

**사용한 문구**:
> "있는지 확인해줘"가 아니라 — "Mapper의 `${}` 바인딩부터 Service, Controller까지
> 한 줄씩 역추적해줘. 추적이 막히는 지점이 있으면 추측하지 말고 '추적 불가: 이유'로
> 명시해줘."

**결과**: 외부 입력이 실제로 도달하지 않는 후보는 자동으로 오탐 처리(오탐 68건 중
다수가 이 방식으로 걸러짐), 도달이 확인된 건만 근거를 남기고 정탐으로 확정.

---

#### ② 컨텍스트별 XSS 판정 (JSP/Thymeleaf)

**실제 사례**: 화면 출력값에 HTML escape가 적용돼 있었지만, JS 인라인 컨텍스트
에서도 실제로 안전한지는 별도 확인이 필요했던 경우

**사용한 문구**:
> "HTML Body / Attribute / JS 인라인 / URL, 4가지 출력 컨텍스트로 나눠서 표로
> 판정해줘. `fn:escapeXml()`은 HTML 컨텍스트용이라 JS 컨텍스트에는 불충분하다는
> 점을 고려해줘."

**결과**: "escape 돼 있으니 안전"이라는 단순 오판을 방지하고, 컨텍스트별로 실제
위험한 출력 지점만 정탐으로 분리 확정.

---

### 그룹 2 — 판정 근거를 명확히 하는 프롬프트 (위험도가 얼마나 되는가?)

#### ③ 하드코딩 시크릿 진위 판별

**실제 사례**: dev 프로파일 설정에 자격증명이 하드코딩돼 있었는데, 운영과 같은
값인지 확인해야 위험도를 제대로 매길 수 있었던 경우

**사용한 문구**:
> "dev/default 프로파일이면, 운영(production) 프로파일의 같은 설정과 값이
> 동일한지 대조해줘 — 동일하면 운영 자격증명 유출과 같은 위험도로 판정해줘."

**결과**: dev와 운영 자격증명이 실제로 동일한 사례를 발견해 위험도를 Medium에서
High로 상향. 이 판단 기준은 Memory(`feedback_hardcoded_credential_severity.md`)로
확정되어 이후 모든 리뷰에 자동 적용됨.

---

#### ④ CVE 영향도 판단 (소스코드 없이)

**실제 사례**: 오픈소스 라이브러리에서 CVSS 9.8짜리 CVE가 나왔는데, 실제 우리
서비스 구조에서 악용 가능한지 판단이 필요했던 경우

**사용한 문구**:
> "이 CVE가 실제로 악용되려면 어떤 조건이 필요한가? 우리 서비스(REST API, JWT
> 기반 인증)에서 실제 악용 가능성은?"

**결과**: CVSS 점수만으로 매기던 우선순위를 실제 사용 조건 기준으로 재조정 —
소스코드 한 줄 보지 않고도 실질 위험도와 패치 우선순위 판단 가능.

---

### 그룹 3 — 산출물을 자동화하는 프롬프트 (반복 업무를 없애기)

#### ⑤ 반복 작업 기준 자동 문서화

**실제 사례**: 로그 레벨별 PII 노출 위험도를 리뷰마다 반복해서 판단해야 했던 경우

**사용한 문구**:
> "오늘 리뷰에서 아래 기준으로 판정했어: info/warn/error 레벨 로그의 PII는
> 취약/High, debug/trace 레벨은 정보/Medium. 이 기준을 앞으로 자동 적용되도록
> Memory에 저장해줘."

**결과**: `feedback_log_dto_severity_standard.md` 등 5건이 공식 기준으로 확정.
다음 리뷰부터는 같은 질문을 반복하지 않고 AI가 동일 기준을 자동 적용.

---

#### ⑥ 보고서 섹션 자동 작성

**실제 사례**: 취약점 목록은 확정됐는데, 개발팀이 읽을 "취약점 개요" 문장을 매번
새로 쓰기 번거로웠던 경우

**사용한 문구**:
> "독자는 해당 서비스 개발팀(보안 비전문가), 길이는 2~3문장, 구조는 ①주요
> 취약점 현황 → ②실제 위협 → ③조치 권고 순서로 작성해줘."

**결과**: 보고서 초안 작성 시간이 수기 2~3시간에서 자동 생성 5분으로 단축.
담당자는 검토·수정만 수행.

---

### 재사용 가능한 절차 (누구나 따라 할 수 있는 워크플로)

```
Step 0. 전역 방어장치 먼저 확인 (생략하면 판정이 뒤집힐 수 있음)
  → WebFilter / OncePerRequestFilter / HandlerInterceptor 존재 여부를 먼저 검색
  → 전역 XSS 필터(Lucy/AntiSamy)나 입력 검증 필터가 있으면, 이후 개별 취약점
    판정 시 "이 필터를 통과하는가"를 함께 고려해야 정확한 판정이 나온다

Step 1. 코드 준비
  → 분석할 소스코드를 AI가 접근할 수 있는 경로에 배치

Step 2. 스캐너 실행 (선택)
  → 패턴 기반 1차 후보 추출 (grep, semgrep 등)
  → 없으면 AI에게 직접 "이 파일에서 SQL Injection 패턴 찾아줘" 요청

Step 3. AI 교차검증
  → 후보 코드를 AI에게 제시
  → "실제로 악용 가능한지, 입력 경로를 추적해서 확인해줘" 요청

Step 4. 담당자 최종 판정
  → AI 분석 결과를 보고 정탐/오탐 확정
  → 판정 근거를 메모로 남기기

Step 5. 보고서 작성
  → 정탐 목록 + 메모를 AI에게 제공
  → "이 내용으로 보안 보고서 초안 작성해줘" 요청
  → 담당자 검토 후 확정
```

## 6. 사용하면서 느낀 한계와 주의사항

### 한계 1 — AI는 실행 환경을 모른다

**현상**: 코드에는 취약 패턴이 있지만, 실제 운영 환경에서 해당 API가 내부망에만 노출되어 있거나, WAF가 앞단에서 차단하는 경우 — AI는 코드만 보고 "취약"으로 분류

**대응**: 서비스 아키텍처(외부 노출 범위, WAF 유무)는 **담당자가 직접 판단**해야 함. AI의 결과는 참고값

---

### 한계 2 — 컨텍스트 제한으로 대형 레포 분석 품질 저하

**현상**: 수십만 라인 규모 레포에서 코드 흐름이 여러 파일에 걸쳐 있을 때, AI가 전체 경로를 추적하지 못하고 부분적으로만 분석

**실제 사례**: 대형 레포 하나가 API 4,176개 규모라 한 번에 스캔을 걸었더니 처리 도중 timeout 발생 — 한 번에 넘기기엔 너무 큰 범위였다

**대응**: 취약점이 의심되는 파일 범위를 좁혀서 제공. "이 Controller → 이 Service → 이 DAO 순서로 추적해줘"처럼 경로를 사람이 먼저 안내. 대형 레포는 빌드 모듈 단위로 쪼개서(모듈당 API 800~1,000개 수준) 나눠 스캔하면 timeout 없이 완료됨

---

### 한계 3 — 할루시네이션 — AI가 없는 코드를 있다고 설명

**현상**: 드물지만, AI가 실제로 존재하지 않는 메서드나 파라미터를 언급하며 취약점을 설명하는 경우 발생

**대응**: 중요 판정은 항상 **실제 코드를 직접 열어서 확인**. "코드의 몇 번째 줄이 어떻게 되어 있어?"라고 재질문하여 검증

---

### 한계 4 — 비용과 시간

**현상**: 대형 레포 1개 전체 교차검증 시 Claude API 호출이 수십~수백 회 발생, 처리 시간 30분~1시간 소요

**대응**: 고위험 영역(인젝션, 인증/인가)을 우선 처리하고, 저위험 영역은 스캐너 결과만으로 처리하는 **우선순위 기반 접근**

---

### 한계 5 — AI를 맹신하면 안 된다

**실제 사례**: 스캐너 + AI 모두 "양호"로 분류했지만, 담당자가 실제 코드를 직접 열어보니 인증 우회 가능한 패턴 발견

**핵심 교훈**:
> AI가 "양호"로 분류해도 그대로 믿고 끝내면 안 된다.  
> 최종 승인과 애매한 케이스의 판단 책임은 여전히 사람에게 있다.

---

## 7. 마무리 — AI 전환으로 얻은 성과와 기대효과

### 이번 전환으로 실제로 얻은 것
- 31개 레포 진단을 이론상 2~3개월에서 **3주**로 단축 (병렬 진행 포함)
- 스캔 후보 1,931건을 AI가 1차 처리, 담당자는 최종 248건 판정 + 위험도 조정 13건에만 집중 관여
- 보고서 초안 작성이 수기 2~3시간에서 **자동 생성 5분**으로
- 판단 기준이 Memory(`feedback_*.md`)로 축적되어 **담당자가 바뀌어도 기준이 그대로 유지**되는 조직 자산이 됨

### 정확한 협업 구조
AI는 탐지뿐 아니라 실제 취약 여부에 대한 1차 판단과 보고서 초안 작성까지 수행한다.
담당자의 역할은 "AI가 못 하는 판단을 대신하는 것"이 아니라, **AI 결과를 최종
확인·승인하고 애매한 예외 케이스를 판단하는 것**이다. "AI는 탐색만 하고 사람이
판단한다"는 표현은 절반만 맞다 — 실제로는 AI가 판단의 상당 부분을 수행하고, 사람은
그 판단을 검증하고 책임지는 최종 승인자 역할을 한다.

### 기대 효과 (향후)
- 이번에 정리한 6가지 프롬프트와 Step 0~5 워크플로는 보안 진단 외 **다른 반복 검토
  업무**(코드 리뷰, 컴플라이언스 점검 등)에도 그대로 적용 가능
- 신규 레포가 추가돼도 동일 워크플로로 즉시 진단 착수 가능 — 온보딩 비용 감소
- Memory에 축적된 기준이 늘어날수록 담당자가 매번 새로 판단해야 하는 범위는 계속 줄어드는 구조
